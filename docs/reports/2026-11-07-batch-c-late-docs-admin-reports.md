## Поздние документы

**Что считается поздним документом.** Чек или возврат, который пришёл **синхронизацией** (`/sync/push`), когда его смена уже закрыта. Онлайн `POST /sales` в закрытую смену по-прежнему получает 409: касса на связи пробивает в открытую смену. На этом поведении держится и старый тест.

**Что происходит при приёме:**
- документ принимается в **свою** закрытую смену, в чеке `afterClose` = true;
- ожидаемые наличные смены (`expectedCash`) **пересчитываются**: на начало + наличные продаж − наличные возвратов, по всем чекам смены;
- посчитанные кассиром (`closingCash`) **не меняются**;
- смена помечается `changedAfterClose` = true;
- в журнал `shift_changes` пишется запись: документ, его наличные, было, стало, кто, когда;
- в ответе синхронизации — `accepted` и пояснение `note`.

**Поздний возврат больше проданного** не отклоняется: он принимается, а в чеке заполняется `reviewReason`. Остаток растёт на возвращённое — это факт, его видно в отчёте «поздние возвраты на разбор».

**Кто это делает:** пересчёт, пометку и журнал делает **база**, триггером на строках чека. Приложение не может:
- записать в журнал;
- поправить закрытую смену напрямую;
- вставить чек в закрытую смену «не поздним» или открытую — «поздним».

Единственное разрешённое изменение закрытой смены — пересчёт этим триггером, и значение обязано совпасть с пересчётом по данным. Проверено тестом: прямые `UPDATE` смены и `INSERT` в журнал ролью приложения база отклоняет.

**Порядок:** поздние документы одной смены принимаются по очереди (блокировка на смену), иначе два параллельных пересчёта взаимно блокировались бы.

## Отчёты (шаг 7)

**Общие правила:**
- день — по **местному времени филиала** (`stores.timezone`);
- период — `from` … `to` включительно, до 400 дней;
- **финансовые отчёты** (продажи, расхождения, смены, поздние возвраты) — владелец, администратор, менеджер; без `storeId` — по всем филиалам;
- **складские отчёты** (остатки, сроки, минус) — они же и кладовщик; по одному филиалу: `storeId` или филиал из токена; страницами по 500 с курсором `next`;
- кассир — 403 на все.

| Отчёт | Что показывает |
|---|---|
| `GET /reports/sales` | по дням и филиалам: чеки, возвраты, выручка, возвраты денег, чистая выручка, себестоимость (скопирована в строки чека), прибыль; плюс итог |
| `GET /reports/price-mismatches` | строки, пробитые не по цене листа: цена, цена листа, разница × кол-во; итог |
| `GET /reports/shifts` | смены: наличные на начало, посчитано кассиром, ожидалось, разница, `changedAfterClose`, число поздних документов; `changedOnly=true` — только изменённые после закрытия |
| `GET /reports/late-returns` | поздние возвраты больше проданного — на разбор, с причиной |
| `GET /reports/stock` | остатки филиала с ценой и себестоимостью |
| `GET /reports/expiring?days=N` | что истекает в ближайшие N дней (по умолчанию 7); `expired=true` — и уже просроченное за 90 дней, если оно ещё числится |
| `GET /reports/negative-stock` | отрицательные остатки, самые большие минусы первыми |

**Сколько осталось в партии** считается по FIFO по сроку: продаётся сначала то, что истекает раньше. Поэтому остаток пары лежит в самых поздних партиях. Пример из теста:
- две партии по 5 шт, сроки через 3 и через 20 дней;
- продано 2 → через 3 дня истекут **3** шт;
- продано 6 → ранней партии уже нет, в поздней 4.

## Нужно решение

**Возврат больше проданного, пришедший синхронизацией в ещё открытую смену**, сейчас отклоняется (`rejected`), как и раньше. Пометка «на разбор» вместо отказа сделана только для поздних документов (в закрытую смену), как ты описал. Но возврат, сделанный без связи, — такой же свершившийся факт: деньги отданы, даже если смена ещё открыта. Распространить пометку на все возвраты из синхронизации? Это одна строка в коде, схему не меняет.

## Ограничения

- **Продажи сразу по всем филиалам — 450–550 мс** на базе ×3, по одному филиалу — 170 мс. Время растёт линейно с числом чеков. Продуктовый магазин с 1 000 чеков в день даст около 365 000 чеков на филиал в год (в 10 раз больше, чем в ×3), это порядка 1.5 с. Решение — дневные итоги, как договорились, во втором этапе.
- **В отчёте остатков нет итоговой суммы:** сумма по миллиону строк филиала — 3.3 с. Нужна та же предварительная агрегация.
- **Менеджер может менять доступ к филиалам любому сотруднику фирмы, включая владельца и себя.** Если нужно ограничить (например, менеджер — только кассиров своего филиала), это правило в коде.
- **Весовые префиксы кассиру недоступны (403, по заданию).** Касса без связи разбирает весовой штрихкод сама, поэтому префиксы ей нужно отдавать через синхронизацию — добавлю, когда дойдём до кассы.
- **Сроки годности считаются по FIFO по сроку.** Если продают не по порядку (берут свежее), фактический остаток старой партии больше расчётного: отчёт покажет меньше просрочки, чем есть. Точнее — только учёт партии в каждой продаже, это отдельное решение.
