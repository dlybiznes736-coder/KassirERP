# Kassir ERP — поиск товара по названию через индекс

Дата: 2026-11-07 · PostgreSQL 16.4 в Docker · роль `kassir_app`, RLS включён, как в API.
Скрипты: [search_explain.sql](search_explain.sql) (планы и время в базе), `tools/KassirERP.ApiBench` (через API), миграция [0003_product_search.sql](../migrations/0003_product_search.sql).

**Итог: поиск через API — 2.7–4.1 мс вместо 46–56 мс, и при втрое большем числе товаров время почти не растёт.**

## Почему индекс не использовался

`pg_trgm` и GIN-индекс `ix_products_name_trgm` были в схеме с версии 1, но под RLS не использовались никогда. Оператор `ILIKE` (функция `texticlike`) не помечен `LEAKPROOF`. Postgres не проверяет такие условия через индекс раньше политики RLS `tenant_id = current_tenant_id()`. Получался `Seq Scan` по всем товарам базы.

Один и тот же запрос «кроссовки» на базе 1×:

| Кто выполняет | План | Время |
|---|---|--:|
| `postgres` (RLS обходит) | `Bitmap Index Scan on ix_products_name_trgm` | 34 мс |
| `kassir_app` (RLS) | `Seq Scan on products` | 86 мс |
| `kassir_app`, `enable_seqscan = off` | индекс только по `tenant_id`, trigram — нет | 48 мс |

Составной индекс с `tenant_id` упирается в то же самое, поэтому планировщик его и не брал.

## Что сделано (миграция 0003)

- **Функция `catalog.search_products(query, limit)`, `SECURITY DEFINER`, только для поиска.** Внутри неё RLS не мешает выбору плана. Фильтр по тенанту записан явно: `tenant_id = current_tenant_id()`, то есть тенант по-прежнему приходит только из `TenantDb`. Если тенант не задан, функция возвращает пусто; это проверяют `smoke.sql` и тест `Search_never_returns_other_tenant_products`.
- **Индекс `ix_products_search` — GIN `(tenant_id, name gin_trgm_ops)`**, частичный, `WHERE deleted_at IS NULL` (`btree_gin` для uuid). Старый `ix_products_name_trgm` удалён.
- **Смысл ответа немного изменился.** Если совпадений больше 50, возвращаются 50 любых, отсортированные по названию, а не первые 50 по алфавиту. Иначе частый запрос («кроссовки» — 10 % товаров) должен отсортировать все совпадения, и время снова растёт вместе с числом товаров. Кассир, увидев 50 результатов, уточняет запрос.
- **Поиск — от 3 символов.** Из двух букв не получается ни одной полной триграммы, и индекс не помогает. Две буквы без совпадений («zq») на 150 000 товаров — 120 мс, и время растёт линейно. Три буквы без совпадений — 0.6 мс. Ограничение стоит и в API (400), и в самой функции.
- `%`, `_`, `\` в запросе ищутся буквально: экранирование внутри функции.

## База: до и после, 1× и 3× товаров

Медиана 15 прогонов `EXPLAIN ANALYZE` (планирование + выполнение) под `kassir_app`. База 1× — `generate.sql` (50 000 моделей, 500 000 пар); база 3× — `generate.sql -v products=150000` (150 000 моделей, 1 500 000 пар). Каждая база снята до и после миграции 0003 на одних и тех же данных.

| Запрос | До, 1× | До, 3× | Рост | **После, 1×** | **После, 3×** | Рост |
|---|--:|--:|--:|--:|--:|--:|
| редкий «кроссовки runner» | 44.7 мс | 131.6 мс | ×2.9 | **1.8 мс** | **2.6 мс** | ×1.5 |
| частый «кроссовки» | 45.7 мс | 132.2 мс | ×2.9 | **1.6 мс** | **1.5 мс** | ×1.0 |
| короткий «run» | 37.9 мс | 109.2 мс | ×2.9 | **1.4 мс** | **1.9 мс** | ×1.4 |

До миграции время росло ровно пропорционально числу товаров (×2.9 при ×3). После — частый запрос не растёт совсем. Редкий и короткий растут в 1.4–1.5 раза: GIN читает все совпадения из индекса (их становится втрое больше), но это дешёвые списки в индексе, а не строки таблицы.

### Планы

**До** (1×, «кроссовки»): полный проход по таблице, 50 114 строк отброшено фильтром.

```
->  Seq Scan on products  (actual time=0.024..43.797 rows=4886 loops=1)
      Filter: ((deleted_at IS NULL) AND (tenant_id = (NULLIF(current_setting('app.tenant_id'...)))::uuid) AND (name ~~* '%кроссовки%'::text))
      Rows Removed by Filter: 50114
Execution Time: 46.569 ms
```

**После** (3×, внутренний план функции, `auto_explain`):

```
-- «кроссовки runner» (редкий): индекс
->  Bitmap Index Scan on ix_products_search  (actual rows=261 loops=1)
      Index Cond: ((tenant_id = 'c0000000-…'::uuid) AND (name ~~* '%кроссовки runner%'::text))

-- «run» (короткий): индекс
->  Bitmap Index Scan on ix_products_search  (actual rows=2585 loops=1)
      Index Cond: ((tenant_id = 'c0000000-…'::uuid) AND (name ~~* '%run%'::text))

-- «кроссовки» (частый): обход товаров фирмы до 50-го совпадения
->  Index Scan using ix_products_category on products p  (actual rows=50 loops=1)
      Index Cond: (tenant_id = 'c0000000-…'::uuid)
      Filter: ((deleted_at IS NULL) AND (name ~~* '%кроссовки%'::text))
      Rows Removed by Filter: 346
```

Для частого запроса планировщик сам выбрал другой путь, и это правильно. Если совпадает каждый десятый товар, быстрее пройти товары фирмы подряд и остановиться на 50-м совпадении (≈ 400 строк), чем собирать все 15 000 совпадений из GIN. Оценку частоты он берёт из статистики. Когда совпадений мало, выбирается GIN (редкий запрос, «run», три буквы без совпадений — 0.6 мс).

## Лимит запросов на /auth/* с одного IP

Был fixed window **30 в минуту**. Для магазина на 50 касс за одним NAT это не годилось: все кассы приходят с одного адреса, и в начале смены 31-й кассир получил бы 429.

Стало — **token bucket: запас 200, пополнение 60 в минуту** (`AuthRateLimitOptions`, секция `RateLimits:Auth`).

- **Почему 200.** Худший всплеск — начало смены: 50 входов по PIN почти одновременно, и у каждого кассира до 3 ошибок ввода до блокировки на 5-й. 50 × (1 + 3) = 200: весь всплеск проходит без отказа. Тест `Fifty_cashiers_behind_one_nat_start_a_shift_without_429`: 50 кассиров разом, у каждого 2 ошибки и вход — 150 запросов, ни одного 429.
- **Почему 60 в минуту.** После начала смены входов почти нет: токен по PIN живёт смену (12 ч). Повторный вход — после перезапуска кассы или смены кассира. За 3–4 минуты запас восстанавливается полностью.
- **Сверх лимита** — 429 с `Retry-After` (тест `Requests_over_the_limit_get_429_with_retry_after`).

**От перебора PIN этот лимит не защищает, и это нужно решить.** Основная защита — блокировка учётки: 5 попыток на 15 минут, это 480 попыток в сутки на учётку. Посчитаю для фирмы на 50 кассиров, если злоумышленник знает код фирмы и логины. Лимит по IP разрешает 86 400 попыток в сутки, этого хватает на все 50 учёток сразу. Шанс угадать 4-значный PIN одной учётки за сутки — 480 / 10 000 ≈ 5 %. Шанс, что за сутки падёт хотя бы одна из 50 учёток, — около 90 %.

Что предлагаю (в эту задачу не входит): вход по PIN только с зарегистрированной кассы. Касса получает свой долгоживущий токен устройства при подключении к филиалу, а PIN лишь определяет, кто из кассиров за ней. Тогда PIN без устройства бесполезен, и вопрос NAT для PIN снимается.

За обратным прокси (nginx и т.п.) нужен `UseForwardedHeaders`, иначе все клиенты для лимита — один IP прокси.

## Фирма и пользователь `bench`

Их создаёт **только `generate.sql`**: код фирмы `bench` у основного тенанта и пользователь `bench` (кладовщик филиала 1, хеш пароля записан в генераторе). Проверено:

- пустая база, собранная только из схемы и миграций 0002–0003 (`create_database.sh`), — `tenants` 0 строк, пользователей `bench` 0;
- в `kassir_schema_v1.sql` и `db/migrations/*.sql` слово `bench` встречается только в одном комментарии (ссылка на `bench.sql`);
- `KassirERP.ApiBench` в базу больше не пишет: раньше он сам создавал этого пользователя, теперь только входит.

## Что ещё нашлось и исправлено по ходу

- **Пул соединений.** По умолчанию у Npgsql до 100 соединений, ровно `max_connections` Postgres. Всплеск запросов к одному экземпляру API съедал все соединения базы, и новые запросы получали 500 (`too many clients already`). Это нашёл тест на 50 касс. Теперь потолок 30 на экземпляр, если в строке подключения не задано иное; лишние запросы ждут соединение, а не падают.
- **`/dev/shm` в Docker.** По умолчанию 64 МБ, и `VACUUM` в генераторе на базе 3× упал: «could not resize shared memory segment». Теперь `shm_size: 512mb` в `docker-compose.yml`.
