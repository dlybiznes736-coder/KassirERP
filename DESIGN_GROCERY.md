# Kassir ERP — продуктовая розница: проектные решения

Дата: 2026-11-07 · Статус: предложение, кода нет · Основа: схема v1 + миграции 0002–0003

Основные клиенты — мини-маркеты, супермаркеты и гипермаркеты. Ниже четыре решения, по одной рекомендации на каждое. В конце — какие из них ломают уже закрытую схему.

**Коротко: ломает схему только регистрация касс (п. 4)** — `device_id` из текста становится ссылкой на кассу. Весовой товар (п. 1) смягчает два ограничения пары (размер и цвет), но существующие данные и код не ломает. Сроки годности (п. 2) и фискализация (п. 3) только добавляют новое.

## 1. Весовой товар

**Рекомендация: один формат весового штрихкода EAN-13 `PP CCCCC WWWWW K`, вес в граммах. Товар ищется по коду PLU, количество в чеке — в килограммах с тремя знаками.**

- **Формат.** `PP` — префикс 20–29: по стандарту GS1 это диапазон для внутренних кодов магазина. `CCCCC` — код товара (PLU), который весы печатают на этикетке. `WWWWW` — вес в граммах. `K` — контрольная цифра EAN-13. Пример: `22 01234 01250 K` → PLU `01234`, 1.250 кг. Префиксы, на которых работают весы, настраиваются для фирмы; по умолчанию все 20–29.
- **Как скан его разбирает.** Сначала ищется точное совпадение штрихкода (индекс `ux_variants_barcode`): так работают обычные товары, в том числе чужие коды с префиксом 2x. Не нашлось, код из 13 цифр, префикс весовой и контрольная цифра верна — тогда PLU = цифры 3–7, вес = цифры 8–12. Пара ищется по `(tenant_id, plu)`, в ответе скана приходит количество = вес / 1000. PLU не найден — 404, как для неизвестного штрихкода.
- **Цена.** Берётся из нашего справочника, цена за кг × вес, округление до тыйына. Цена, напечатанная весами, не используется. Значит, весы должны получать цены из каталога; это отдельная задача.
- **В товаре:** `product_variants.unit` (`pcs` | `kg`, по умолчанию `pcs`) и `product_variants.plu` (уникален в фирме, есть только у весовых).
- **В строке чека:** `qty` — килограммы (`numeric(14,3)` уже позволяет граммы — это решение было заложено раньше), `price` — цена за кг. Добавляются `unit` и `scanned_code` — копия единицы и полный отсканированный код, по принципу 5 «копируем в документ». Код нужен для возвратов и разбора спорных чеков. `total` = round(`price` × `qty`, 2) − скидка.
- **Остатки и приход** — в кг, без изменений: `stock`, `stock_movements` и `purchase_items` уже хранят `numeric(14,3)`.

**Что меняется в схеме:**
- новые колонки `product_variants.unit` и `plu` с частичным уникальным индексом `(tenant_id, plu)`;
- `sale_items.unit`, `sale_items.scanned_code`;
- таблица `weight_barcode_prefixes` (`tenant_id`, `prefix`) с RLS;
- **касается закрытой схемы:** `product_variants.size` и `color` сейчас `NOT NULL` и входят в уникальный индекс `(product_id, size, color)`. У продукта нет ни размера, ни цвета. Делаем их необязательными, индекс пересоздаём с `NULLS NOT DISTINCT` — тогда у товара может быть ровно одна пара без размера и цвета. Существующие обувные данные это не затрагивает, но в API меняется проверка: размер и цвет обязательны только для обуви.

## 2. Сроки годности при приёме товара (минимум для шага 4)

**Рекомендация: срок годности хранится у строки прихода и копируется в движение. Партии при продаже не ведём. Что скоро истечёт — оценка по принципу FIFO.**

- При приёмке накладной для товаров с `product_variants.tracks_expiry = true` срок годности обязателен в каждой строке.
- Триггер приёмки копирует `purchase_items.expires_on` в `stock_movements.expires_on`. Журнал по-прежнему только пополняется.
- Отчёт «истекает в ближайшие N дней» по каждой паре в филиале. Берём текущий остаток S и идём по приходам от новых к старым, пока их сумма не покроет S. Эти приходы и считаются «ещё на полке», а их сроки — сроками остатка. Всё старше считается проданным.
- Ограничение: оценка верна, если товар уходит в порядке поступления. Если покупатели берут свежее с задней полки, просроченного на деле больше, чем в отчёте. Учёт партий при продаже (касса выбирает партию) — отдельный шаг, если понадобится; эта схема его не исключает.

**Что меняется в схеме:**
- `purchase_items.expires_on date`;
- `stock_movements.expires_on date`; колонка без значения по умолчанию, поэтому старые строки не переписываются и журнал не трогается;
- `product_variants.tracks_expiry boolean NOT NULL DEFAULT false`;
- частичный индекс по `(tenant_id, store_id, expires_on)` для строк, где срок указан и движение приходное;
- новая версия функции `trg_purchase_accept`.

Всё только добавляется, ничего существующего не ломается.

## 3. Фискализация онлайн-ККМ в Кыргызстане

**Что требуется сейчас (по открытым источникам):**
- Кассы — онлайн-ККМ с фискальным модулем (сим-карта или облачный). Технические требования ГНС к ККМ с фискальным модулем — приказ № 170 от 18.04.2022, регламент регистрации и снятия ККМ — приказ № 232 от 26.05.2022, порядок интеграции с системой администрирования ККМ — приказ № 118 от 18.02.2025. Использовать можно только модели из реестра ККМ.
- Данные кассы передаёт в ГНС оператор фискальных данных (ОФД). У ГНС есть и своя бесплатная программная ККМ. Коммерческие ОФД (например, eKassa от Telemedia Group) дают REST API для автоматической фискализации чеков из сторонних систем.
- **Новое для продуктовой розницы.** Постановление Кабмина от 4 ноября 2026 года обязывает магазины подключаться к фискальному ПО с передачей данных. Для магазинов с торговым залом больше 100 кв. м (супермаркеты, гипермаркеты) — с **1 августа 2028**, для магазинов в торговых центрах — с **1 февраля 2029**.

**Рекомендация: сами кассой (ККМ) не становимся. Фискализуем через REST API облачной ККМ одного ОФД, адаптером на сервере, который берёт чеки из очереди.**

- Регистрация своей ККМ — это сертификация и включение в реестр; для первого года это неподъёмно. Облачная ККМ ОФД уже в реестре и сама передаёт данные в ГНС.
- **Как это ложится на «интеграции только через очередь».**
  1. Чек приходит на сервер, как сейчас.
  2. В той же транзакции, где сохраняется чек, создаётся строка `fiscal_receipts` со статусом `pending`.
  3. Воркер берёт ожидающие строки (`FOR UPDATE SKIP LOCKED`, как `sync_outbox`), вызывает API ОФД и записывает результат: номер фискального документа, фискальный признак, ссылку для QR.
  4. Результат возвращается на кассу обычной синхронизацией.
  5. Повторы с задержкой — через `attempts` и `next_attempt_at`. Идемпотентность — по нашему `sale_id`, если ОФД принимает внешний ключ; это надо уточнить.
- Касса печатает чек с QR, когда ответ ОФД пришёл, обычно за 1–2 с при живой связи. Без связи продажа не останавливается: чек уходит в очередь и фискализуется позже.

**Вопросы, которые нужно закрыть с ГНС и ОФД до начала работ:**
- **Законна ли отложенная фискализация** для чека, пробитого без связи, и в какой срок она должна случиться. От этого зависит, можно ли кассе продавать офлайн в фискальном режиме.
- **Ставки налогов в чеке.** Какие нужны: НДС, налог с продаж (НсП) по видам деятельности — и на каком уровне их задавать.
- **Хранение фискальных данных у нас.** Проект постановления о фискальном ПО (вынесен на обсуждение 19.08.2026) предлагает запретить передачу и миграцию фискальных данных в стороннее ПО. При этом интеграции с внутренними системами бизнеса остаются возможны, если они не позволяют менять или скрывать фискальные данные и не мешают их передаче в ГНС. Мы храним только реквизиты ответа ОФД (номер, признак, QR) и ничего в них не меняем. Нужно подтвердить, что итоговый текст это допускает.
- **Какой ОФД.** Выбрать одного по документации API, условиям и цене.

**Что меняется в схеме:**
- новая таблица `fiscal_receipts`: `id`, `tenant_id`, `sale_id` (уникален), `device_id`, `status`, `request jsonb`, номер документа, фискальный признак, QR, `attempts`, `last_error`, `next_attempt_at`, `fiscalized_at`; RLS;
- `devices.kkm_registration` — регистрационный номер ККМ кассы у ОФД;
- в `sale_items` копируются ставки налогов (`vat_rate`, `sales_tax_rate`);
- в товаре — налоговая категория.

Чеки и строки чека после записи не меняются — результат фискализации живёт в отдельной таблице, поэтому запрет на изменение проведённого чека не нарушается. Всё только добавляется. Зависит от п. 4: фискализация привязана к зарегистрированной кассе.

## 4. Вход по PIN только с зарегистрированной кассы

**Рекомендация: касса один раз подключается к филиалу по одноразовому коду и получает свой секрет. Вход по PIN принимается только вместе с этим секретом; фирму и филиал определяет касса, а не запрос.**

**Регистрация кассы:**
1. Менеджер или администратор, вошедший по паролю, создаёт в вебе код подключения для своего филиала: 8 цифр, действует 10 минут, одноразовый. Хранится только хеш.
2. На кассе вводят код: `POST /devices/enroll { code, name }`. Сервер создаёт запись в `devices` (филиал — тот, для которого выдан код) и **один раз** возвращает `deviceId` и `deviceSecret` — 32 случайных байта.
3. Касса хранит секрет в защищённом хранилище ОС (DPAPI в Windows, Keystore в Android). В базе — только хеш секрета: секрет случайный и длинный, поэтому соли и PBKDF2 не нужно, хватает SHA-256.
4. Менеджер может отключить кассу, тогда у неё заполняется `revoked_at`.

**Что меняется в `/auth/pin`:**
- Запрос — только `{ login, pin }`, касса подтверждается заголовком `Authorization: Device <deviceId>.<deviceSecret>`. Код фирмы в запросе больше не нужен: фирму и филиал определяет касса.
- Неизвестная или отключённая касса — 401, без проверки PIN. PIN подходит, только если кассир привязан к филиалу кассы (или ко всем филиалам).
- Лимит частоты — по кассе, а не по IP. Вопрос с 50 кассами за одним NAT для PIN исчезает. Лимит по IP остаётся на `/auth/login` и `/devices/enroll`.
- В токене появляется `device_id`. Отключение кассы действует сразу: API держит в памяти список отключённых касс, обновляет его раз в 30 с и отклоняет их токены. Без этого украденная касса работала бы до конца смены — токен живёт 12 часов.
- Подбор PIN без самой кассы невозможен. С кассой его по-прежнему останавливает блокировка учётки: 5 попыток на 15 минут.

**Что меняется в схеме:**
- новые таблицы `devices` (`id`, `tenant_id`, `store_id`, `name`, `secret_hash`, `kkm_registration`, `registered_by`, `registered_at`, `last_seen_at`, `revoked_at`) и `device_enrollments` (код подключения: хеш, срок, кем выдан, когда использован), обе с RLS;
- функции входа в схеме `auth`: проверка кассы и выдача кода. До токена фирма неизвестна, поэтому, как и вход по паролю, это `SECURITY DEFINER`;
- **ломает закрытую схему:** `device_id` сейчас — произвольный текст в `cash_shifts`, `sales` и `sync_outbox` и входит в индексы `ux_sales_device_number` и `ux_shifts_open_per_device`. Он становится `uuid` со ссылкой на `devices`. Иначе любая касса может записать продажу от имени чужой: сейчас `device_id` приходит в теле запроса, а должен браться из токена.

## Какие пункты ломают закрытую схему

| Пункт | Что затрагивает в существующей схеме | Ломает? | Как вводить |
|---|---|---|---|
| 1. Весовой товар | `product_variants.size`, `color` перестают быть обязательными; индекс `(product_id, size, color)` пересоздаётся с `NULLS NOT DISTINCT` | Нет: ограничение только смягчается, старые данные и код продолжают работать. Меняется проверка в API | Одна миграция |
| 2. Сроки годности | Новые колонки без значения по умолчанию в `purchase_items` и `stock_movements`; новая версия `trg_purchase_accept` | Нет | Одна миграция |
| 3. Фискализация | Только новые таблицы и колонки; проведённые чеки не меняются | Нет, но нужен п. 4 | После п. 4 |
| 4. Регистрация касс | Тип `device_id` в `cash_shifts`, `sales` и `sync_outbox`: текст → `uuid` со ссылкой на `devices`; два уникальных индекса; запрос `/auth/pin` | **Да** | Сейчас, пока нет живых установок: одной миграцией, тестовые данные пересоздаются генератором. После первого клиента — только в два релиза, по правилу ТЗ |

Предлагаемый порядок: **4 → 1 → 2 → 3**. Регистрация касс ломает схему, поэтому её лучше сделать до живых клиентов; фискализация зависит от касс; весовой товар и сроки нужны продуктовому магазину с первого дня.
