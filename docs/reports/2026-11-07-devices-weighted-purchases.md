# Партия: регистрация касс, весовой товар, приём товара (шаг 4)

**Итог: три шага сделаны. 67 тестов проходят — 42 прежних и 25 новых. Скан через API не замедлился. Миграции перенесли 113 тысяч чеков и 1 460 смен на новые кассы без потерь.**

## Что сделано

| Шаг | Миграция | Что появилось |
|---|---|---|
| Регистрация касс | `0004_devices.sql` | Таблицы `devices` и `device_enrollments`. Код подключения: 8 цифр, 10 минут, одноразовый; выдаёт менеджер, вошедший **по паролю**. Касса обменивает код на свой id и секрет. `/auth/pin` принимает только `{ login, pin }` + заголовок `Authorization: Device <id>.<secret>`; фирму и филиал определяет касса. Отключение кассы: токены её кассиров перестают работать сразу. Лимит на вход по PIN — по кассе, а не по IP. |
| Весовой товар | `0005_weighted_goods.sql` | Размер и цвет необязательны. `unit` (`pcs`/`kg`) и `plu` у пары. Скан разбирает `PP CCCCC WWWWW K` (префиксы 20–29, контрольная цифра EAN-13) и возвращает количество в кг и сумму строки. `weight_barcode_prefixes` — какие префиксы отданы весам; пусто — все 20–29. |
| Приём товара | `0006_purchase_expiry.sql` | `POST /purchases` (черновик), `PUT /purchases/{id}/items`, `DELETE`, `POST /purchases/{id}/accept`. Срок годности — в строке и в движении склада. `tracks_expiry` у пары делает срок обязательным. Повторная отправка той же накладной или проведения не создаёт дубль. |

**Что ломает закрытую схему (как и предупреждал DESIGN):**
- `device_id` в `cash_shifts`, `sales` и `sync_outbox` из текста стал `uuid` со ссылкой на `devices`. Миграция переносит данные: на каждое старое имя кассы создаётся касса без секрета. Войти с такой кассы нельзя, её нужно подключить заново.
- Контракт `/auth/pin`: кода фирмы в теле больше нет. Старый запрос с `tenantCode` получает 400.

Попутно сделано:
- **Приход принимает пары только своей фирмы.** Строка накладной не может сослаться на пару чужой фирмы: проверка и в API, и триггером в базе. Внешний ключ проверяет существование строки в обход RLS и такую ссылку пропустил бы.
- **Новые миграции подхватываются сами** при создании тома Docker (`db/initdb/00_apply_schema.sh`), править `docker-compose.yml` больше не нужно.
- **Стенд для ручной проверки** — `db/bench/_bench_stand.sql`, его создаёт только генератор: менеджер `bench`, PIN `1234` у кассиров, весовая колбаса с PLU `01234`.

## Не сделано и известные ограничения

- **Фискализация** — отложена, как решено.
- **Отчёт «истекает в ближайшие N дней»** (оценка FIFO из DESIGN, п. 2) — не делал: в шаг 4 входил только срок в строке. Данные для отчёта уже копятся в `stock_movements.expires_on`, есть индекс `ix_movements_expiry`.
- **Префиксы весов** настраиваются только через SQL (`weight_barcode_prefixes`), API для этого нет.
- **Цена с весов не используется**, цена берётся из каталога. Выгрузки цен на весы нет.
- **Секрет кассы хранится как SHA-256 без соли.** Это осознанно: секрет — 32 случайных байта, перебрать его нельзя.
- **Подмена id кассы в заголовке** даёт злоумышленнику новый счётчик лимита, но такой запрос получает 401 до проверки PIN. Подобрать PIN это не помогает, а нагрузка — одна дешёвая выборка по ключу.
- **Ссылки на чужую фирму через внешний ключ.** Защиту на уровне базы я добавил только для строк прихода. Для строк чека и других таблиц то же самое — при работе над продажами.
- **Старые кассы в твоих базах.** В `kassir` и `kassir_x3` 4 кассы, перенесённые из текстовых имён, без секрета. Если понадобятся — подключить заново по коду.
