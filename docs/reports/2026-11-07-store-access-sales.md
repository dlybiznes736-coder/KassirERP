# Партия: доступ кассира к филиалам, продажа (шаг 5)

Дата: 2026-11-07 · Миграция `0007_user_stores_sales.sql` · Перемещение между филиалами — следующей партией.

**Итог: доступ к филиалам — только явный список. Чек, возврат и смена работают через API. 80 тестов проходят — 67 прежних и 13 новых. Проведение чека через API — p50 7.5–10.2 мс, p95 9.7–14.4 мс (три прогона).**

## Доступ кассира к филиалам — явный список

- **Новая таблица `user_stores`** (сотрудник → филиал, с RLS). Вход по PIN разрешён, только если филиал кассы есть в списке сотрудника. **Пустой список — вход запрещён (403)**. Раньше `users.store_id = NULL` значило «все филиалы».
- **Миграция заполняет список** из `users.store_id`: у кого был филиал, у того он и остался. В твоих `kassir` и `kassir_x3` заполнено 9 из 9.
- **`users.store_id` остался** — это филиал по умолчанию для входа в веб по паролю. Вход по паролю в этой партии не менялся.
- **В базе:** сотрудник и филиал в списке должны быть одной фирмы (триггер). Проверка при входе — функция `auth.user_has_store`, как и остальные функции входа.
- **API для правки списка нет**, только SQL. Нужно будет вместе с управлением сотрудниками.

| Тест | Результат |
|---|---|
| `AuthTests.Cashier_without_stores_cannot_log_in` — кассир без филиалов на кассах филиалов 1 и 2 | 403, 403 |
| `AuthTests.Cashier_with_stores_1_and_2_logs_in_only_there_not_on_store_3` — кассир с филиалами 1 и 2 | касса 1 — 200, касса 2 — 200 (филиал 2 в токене), касса 3 — **403** |

Прежний тест `Pin_login_takes_store_from_the_device` («кассир без филиала входит на кассе любого филиала») по новому правилу неверен — он заменён первым тестом из таблицы. Тест лимита по кассе раньше входил под этим кассиром, теперь — под кассиром с филиалами 1 и 2. Остальные прежние тесты не менялись.

## Продажа (шаг 5)

| Запрос | Что делает |
|---|---|
| `POST /shifts` · `POST /shifts/{id}/close` | Открыть смену (id создаёт касса; на кассе одна открытая смена) и закрыть её. При закрытии считаются ожидаемые наличные: на начало + наличные продаж − наличные возвратов. |
| `POST /sales` | Чек. Строки: штучные (целое количество) и весовые (кг, до грамма, `scannedCode`). Оплаты `cash` / `card` / `transfer` / `other`, несколько в чеке; сумма оплат должна равняться сумме чека. Цена — с кассы (её видел покупатель, касса могла пробить чек без связи); единица и себестоимость копируются из пары. |
| `POST /sales` с `type: "return"` | Возврат отдельным чеком на чек-продажу. Строка возврата — только `returnOfItemId` и количество. Пара, цена и себестоимость берутся из исходной строки, скидка — пропорционально. Вернуть можно не больше проданного с учётом прежних возвратов. |
| `GET /sales/{id}` · `GET /shifts/{id}` | Чек и смена. |

Правила:
- Пробивать чеки и работать со сменой можно только с токеном кассы (вход по PIN на зарегистрированной кассе); вход по паролю — 403. Филиал, касса и кассир берутся из токена.
- Строки чека вставляются **последним оператором перед `COMMIT`** — правило из ТЗ.
- Возвраты одного чека проводятся строго по очереди (advisory lock). Иначе два одновременных возврата вместе могли бы превысить проданное.

**Защита в базе (миграция 0007).** API проверяет всё то же самое раньше и отвечает понятной ошибкой, база — страховка:
- `UPDATE` чека запрещён, как и `DELETE`. Строки и оплаты нельзя менять с версии 1. У роли приложения отозвано право `UPDATE` на `sales`.
- Чек — только в смену своей кассы и своего филиала. Возврат — только на чек-продажу своей фирмы.
- Строка возврата — из исходного чека, той же пары. Вернуть больше проданного нельзя.
- Пара в строке чека — только своей фирмы.
- Закрытую смену нельзя изменить или открыть заново.

**Что ломает в закрытой схеме:**
- **Запрет `UPDATE` на `sales`.** Приложение чеки не правит. Будущим миграциям, которым понадобится переписать чеки, нужен `session_replication_role = replica`, как уже сделано для журнала движений.
- **Смысл `users.store_id = NULL` для входа по PIN** — см. раздел выше.

### Тесты продажи

| Требование | Тест | Результат |
|---|---|---|
| Повторная отправка чека не создаёт дубль | `Resending_the_same_sale_does_not_create_a_duplicate` | 201 → 200 → 200; в базе 1 чек, 2 строки, 1 оплата, 2 движения; остаток уменьшен один раз |

| | `Parallel_returns_cannot_exceed_what_was_sold` | Две кассы одновременно возвращают по 0.7 кг из 1 кг: ровно один 201, один 400 |

Ещё 6 тестов:
- оплата только наличными и только картой;
- сумма оплат не равна сумме чека — 400, дробное количество штучного товара — 400;
- возврат со скидкой: возвращается цена минус пропорциональная скидка (4 500 из 9 000 за одну пару из двух);
- строка возврата из другого чека — 400;
- чек без токена кассы — 403, пара чужой фирмы — 400, чек в закрытую смену — 409;
- закрытие смены: ожидаемые наличные 1 000 + 2 000 − 130 = 2 870.

**Проверка, что тесты ловят то, что должны:**

| Мутация (временно, затем код возвращён) | Результат |
|---|---|
| Убрана проверка «больше проданного» в API | Тесты возврата **прошли**: возврат остановил триггер в базе — страховка работает сама по себе |
| Убрана блокировка возвратов одного чека | `Parallel_returns…` упал в 2 прогонах из 3: гонка настоящая, и её закрывает блокировка |

## Замер: проведение чека через API

`tools/KassirERP.ApiBench --mode sales`, Release, база 1×. Один клиент, запросы подряд, 1 000 чеков и 200 возвратов, три прогона (третий — командой из раздела «Команды», в PowerShell). Всё идёт через API, как у кассы: регистрация, вход по PIN, смена. Чек: пара обуви + весовая колбаса, наличные + карта. Время — от отправки `POST /sales` до последнего байта ответа.

| | p50 | p95 | p99 |
|---|--:|--:|--:|
| Чек: 2 строки, 2 оплаты | 7.48 / 10.23 / 8.18 мс | 9.68 / 13.01 / 14.43 мс | 12.32 / 15.84 / 19.08 мс |
| Возврат: 1 строка | 7.96 / 11.73 / 8.61 мс | 9.59 / 15.25 / 11.73 мс | 11.50 / 22.25 / 15.93 мс |

Для сравнения, скан через API — около 1 мс. Чек дороже по двум причинам:
- **около 9 сетевых обменов с базой:** проверка повтора, смена, пары, чек, оплаты, строки, чтение итога, `COMMIT`;
- **`COMMIT` с записью на диск** — чек должен пережить сбой.

Сократить обмены можно, объединив проверки в один пакет. Это задача оптимизации, если понадобится; цель кассы «быстрее 100 мс» выполняется с запасом.

**Конкурентный тест после 0007.** Новые проверки в базе срабатывают на каждый чек, поэтому прогнал `db/bench/concurrency` заново — по 30 с на сценарий. Для сравнения — `CONCURRENCY_REPORT.md` до этой партии (по 60 с на сценарий).

## Цены в разных филиалах — ответ без кода

**Сейчас.** Цена одна на пару для всей фирмы: `product_variants.sale_price`. У филиала своих цен нет. В ТЗ это отложено на этап 2 как таблица `price_lists`. Касса может пробить чек по своей цене — сервер её принимает (касса работает и без связи), а в чек копируется фактическая цена. Поэтому история продаж уже защищена, но управлять разными ценами негде.

**Рекомендация: прайс-листы, назначаемые филиалам, а не цены на каждый филиал.**
- `price_lists` (фирма, название) и `price_list_items` (прайс-лист, пара, цена).
- У филиала — ссылка на прайс-лист. Нет ссылки или нет цены в листе — действует базовая цена пары.
- Сеть на 50 магазинов обычно живёт в 2–5 ценовых зонах (город, область, торговый центр). Правят 3 листа, а не 50 филиалов; новый филиал — выбрать лист.
- Скан получает цену одним дополнительным поиском по ключу (лист, пара) — на время скана это не влияет. Касса при синхронизации получает цены своего листа.
- Изменения цен пишутся в журнал (кто, когда, было, стало), сами цены в листе — текущие. Цены с датой начала действия — только если появится потребность.
- Схему не ломает: только новые таблицы и одна колонка у филиала.

## Не сделано и известные ограничения

- **Цену с кассы сервер не сверяет с каталогом.** Касса работает и без связи, поэтому в чек идёт цена, которую видел покупатель. Отчёт о расхождениях с каталогом — вместе с прайс-листами.
- **Список филиалов сотрудника** правится только через SQL, API нет. Вход по паролю пока использует `users.store_id`.
- **Чек — около 9 сетевых обменов с базой.** Их можно сократить, если понадобится.
- **Перемещение между филиалами** — следующей партией, как решено.
